the counts above are measured from scripts/load_graph.py output on the committed snapshot; the ingest asserts every direction by running the flipped pattern and requiring zero rows; a cypher pattern that matches nothing returns zero rows with no error, so a flipped arrow looks like a correct empty answer. that mistake was made here once; it is in bugs i found.

the query the product depends on

// follow up to 3 successor hops from the labelled team to the CURRENT team
MATCH (labelled:Team {slug: $slug})
MATCH (labelled)-[:SUCCEEDED_BY*0..3]->(owner:Team)
WHERE owner.status = 'active'
MATCH (owner)<-[r:LEAD|MEMBER]-(p:Person)
OPTIONAL MATCH (p)-[:AUTHORED]->(authored:RFC)
WITH owner, p, collect(DISTINCT type(r)) AS kinds,
     count(DISTINCT authored) AS authored_count, max(authored.created) AS latest
RETURN owner.slug AS owner, p.handle AS handle,
       CASE WHEN 'LEAD' IN kinds THEN 'lead' ELSE 'member' END AS role,
       authored_count AS authored, coalesce(latest, '') AS latest
ORDER BY latest DESC, authored DESC, handle

the 0 matters as much as the 3: an active label takes zero hops through the same query, so there is no second code path to drift. what breaks without a graph: the relational form of this one question is a recursive CTE for a chain whose depth is not known, plus a filter for the terminal active team, plus the roster join and a grouped max. the stake: 162 of 761 merged rfcs (libs-api 138, core 24, from cmd/gaps.py) resolve only through this hop. without it they return an archived team with an empty roster, which is a dead end, not an answer.
